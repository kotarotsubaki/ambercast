# Secrets in plans

## Authorization {#authorization}

Plans MUST represent secret values only with [[spec/value-types#shared-types]] `SecretRef`; the contiguous `{{secrets.` interpolation marker is forbidden from `InterpolatableText`. [repo:src/core/ir/schema.ts:31-33] [repo:src/core/ir/schema.ts:159]

A committed `fill-secret` MUST contain exactly `target: ElementRef` and `secretRef: SecretRef`. A committed AI step's optional `secrets` array contains `AiStepSecretUse` entries of exactly `{ "ref": SecretRef }`. Neither committed form contains provider naming data, citation data, or prompt-source provenance. [repo:src/core/ir/schema.ts:396] [repo:src/core/ir/schema.ts:489-504] [repo:src/core/ir/schema.ts:667-692]

At run time, `{{secrets.NAME}}` resolves only through `AMBERCAST_SECRET_<NAME>`, after replacing every `.` in `NAME` with `_` and uppercasing it. The resolved value MUST NOT enter the Plan. [repo:src/core/secrets/env-var-name.ts:8-16] [repo:src/adapters/system/env-secrets-provider.ts:14-34]

## Consent and allowlist {#grant-origin}

Generation MUST first construct a candidate Plan, then decide consent before it persists that Plan or its Grounding. The candidate stage locally resolves each provider proposal to a `SecretName`, wraps it as a `SecretRef`, and reports every use; the consent stage admits only names already in `ambercast.config.json` `secrets.allow` or names accepted by the user. [repo:src/usecases/generate.ts:1094-1155] [repo:src/usecases/generate.ts:1405-1424] [repo:src/core/config/schema.ts:78-84]

`SecretName` is the bare logical name used by configuration and consent; `SecretRef` is its `{{secrets.NAME}}` Plan wrapper. A provider-facing `fill-secret` MAY instead carry `secret?: SecretNameChoice`: `{ "allowedName": SecretName }` requests an already projected allowlisted name, while `{ "nameHint": SecretNameHint }` proposes a newly discovered name. `SecretNameChoice` is a strict exclusive union, and `SecretNameHint` is `/^[a-z][a-z0-9_]{0,63}$/`. Provider-facing AI secret uses use the same choice, or an empty strict object when the provider supplies no choice. Local deterministic naming, not a provider reference, produces every committed `SecretRef`. [repo:src/core/ir/schema.ts:83-115] [repo:src/core/ir/schema.ts:729-785] [repo:src/core/ir/schema.ts:813-833] [repo:src/usecases/secret-naming.ts:156-188]

On acceptance, newly accepted names MUST be merged into `secrets.allow`, so later generation skips a further decision for those names. `secrets.allow: "*"` accepts every name and bypasses the consent gate. This wildcard is a deliberately low-friction, high-risk escape hatch: it accepts an arbitrary AI-proposed secret name without per-name review and MUST be used only with that risk understood. [repo:src/usecases/generate.ts:1423-1482] [repo:src/config/write-secrets-allow.ts:52-82]

When `consentMode: "forbid"` is used, generation MUST return a `candidate` result with the proposed Plan and secret uses and MUST NOT write artifacts or request consent. If consent is declined or unavailable because the terminal is non-interactive, generation MUST fail with `SECRET_CONSENT_REQUIRED` and MUST NOT silently persist the candidate. [repo:src/usecases/generate.ts:1251-1257] [repo:src/usecases/generate.ts:1405-1420] [repo:src/usecases/generate.ts:1426-1493] [repo:src/runtime/secret-consent.ts:293-321]

The provider receives projected/negotiated secret names, not secret values. Names can themselves be descriptive (for example, `stripe_api_key`), so this is an accepted provider-disclosure risk; an implementation MUST NOT represent it as value disclosure. [repo:src/usecases/generate.ts:1020-1027] [repo:src/core/ir/schema.ts:83-115]

Heal MUST NOT make a new consent decision. If its Stage 3 full-plan candidate changes the logical secret-name set, it MUST restore its overlay and return the `secret-set-rejected` result branch with `stage3Rejection.reason: "secret-set-changed"`, `added`, and `removed`; its case outcome has `commit: undefined`. The shipped CLI renders this branch's localized hint verbatim: `秘匿値の構成が変わった。ambercast generate --force <file> で再生成し同意を取り直す`. Stage 2 uses the distinct `secret-name-invalid` rejection reason when local naming, allowlist validation, or environment-variable collision prevents a permitted replacement Plan. [repo:src/usecases/heal.ts:191-205] [repo:src/usecases/heal.ts:856-878] [repo:src/usecases/heal.ts:1012-1019] [repo:src/usecases/heal.ts:1296-1314] [repo:src/ports/system.ts:8-33] [repo:src/cli/main.ts:335-354]

## Sink and redaction {#sink-and-redaction}

Secret sink origins MUST be HTTP(S) origins and MUST NOT contain the contiguous `{{secrets.` interpolation marker; this schema constraint does not itself prove the absence of arbitrary secret-looking literals. [repo:src/core/ir/schema.ts:39,130-132] Consumers MUST preserve references rather than literal passwords in committed grounding trace data. [repo:src/core/ir/schema.ts:964-973]

The sink policy parses and normalizes origins at runtime; an absent configured entry for the requested secret in `secretSinkOrigins` allows only `baseUrl`, an empty entry allows none, and a non-empty entry replaces that default. For each actual `fill-secret`, the run pipeline MUST check the live page origin immediately before resolving its secret; the browser adapter MUST repeat the policy after element acquisition and immediately before filling, so navigation or DOM changes cannot bypass the live-origin boundary. [repo:src/core/ir/schema.ts:152-157] [repo:src/usecases/run.ts:765] [repo:src/usecases/run.ts:896] [repo:src/adapters/browser/chromium.ts:413]

## Literal-secret rejection {#literal-secret-rejection}

This section is the canonical owner of literal-secret detector semantics. Reference pages MUST only summarize the detector boundary for their local purpose and link here. Before persistence or report serialization, generation MUST inspect every provider-derived JSON string and object key, including `generatorMeta` and ambiguities, using lexical-key and array-index traversal order. For each string value or object key, an embedded `{{secrets.` marker (SEC-17) MUST be rejected before the four primitive detectors below are checked; among those, the first match in the fixed order below MUST be rejected. [repo:src/usecases/generator-secret-policy.ts:162-232]

| id | detector | matching value | exception | classified failure |
| --- | --- | --- | --- | --- |
| SEC-01 | `credential-prefix-sk` | begins `sk-` | a valid whole-value `SecretRef` in a string value or object key; `source.inputsDigest` only | `SECRET_LITERAL_REJECTED`, exit `2` |
| SEC-02 | `credential-prefix-ghp` | begins `ghp_` | a valid whole-value `SecretRef` in a string value or object key; `source.inputsDigest` only | `SECRET_LITERAL_REJECTED`, exit `2` |
| SEC-03 | `credential-prefix-aws-access-key` | begins `AKIA` | a valid whole-value `SecretRef` in a string value or object key; `source.inputsDigest` only | `SECRET_LITERAL_REJECTED`, exit `2` |
| SEC-04 | `high-entropy-token` | token-shaped (at least 32 UTF-16 code units, no whitespace, every character in `[A-Za-z0-9+/=_.-]`) and Shannon entropy at least 4.0 bits, with frequency keys iterated as Unicode code points but each probability denominator using the UTF-16 code-unit length | a valid whole-value `SecretRef` in a string value or object key; `source.inputsDigest` only; also exempt at a `steps[<index>].url`, `steps[<index>].pattern`, or `targets[<key>].baseUrl` value position | `SECRET_LITERAL_REJECTED`, exit `2` |
| SEC-17 | `embedded-secret-reference` | a string value or object key, other than a valid whole-value `SecretRef`, containing the `{{secrets.` marker | `source.inputsDigest` only | `SECRET_LITERAL_REJECTED`, exit `2` |

A valid whole-value `SecretRef` exempts a string value or object key from every detector in this section; every other key is passed to the detector before its value is traversed. The rejection diagnostic MUST contain only detector and redacted JSON-like path; it MUST NOT retain the detected literal, and a detected object key uses `[redacted-key]`. [repo:src/usecases/generator-secret-policy.ts:182-193] [repo:src/usecases/generator-secret-policy.ts:210-232] [repo:src/report/error-mapping.ts:23] [repo:src/core/errors/exit-codes.ts:31]

## Rationale {#rationale}

The problem is allowing an agent to fill a required credential without turning prompt prose, logs, or UI evidence into a secret channel. Authorization must be auditable and narrow. 

The selected design separates provider discovery from authorization: locally derived candidate names are shown for consent, durable allowlist entries are auditable, and the committed Plan records only whole-value references. It is fail-closed when consent is refused or unavailable, while the sink-origin boundary remains independently enforced.

One rejected alternative embedded authorization syntax in prompt prose and persisted prompt spans; it was rejected because prompt wording is not a durable, reviewable consent control. Another persisted literal values in traces; it was rejected because committed artifacts and diagnostics are long-lived disclosure surfaces.
