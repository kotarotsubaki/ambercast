title: Manage secrets
description: Approve the secret names that generation proposes and pass their values through environment variables.
---

import { Steps, LinkCard } from '@astrojs/starlight/components';

Keep secrets out of the prompt, approve the proposed names, and pass the values through the environment.

## Prerequisites \{#prerequisites}

You do not need an existing `ambercast.config.json`. When accepted consent has to persist the allowlist and the file is absent, ambercast creates it.

## Steps \{#steps}

<Steps>

1. ## Write the prompt without secrets \{#write-prompt}

   Write only the user outcome. Do not write a grant line or a secret value. The generated plan holds only `{{secrets.*}}` references, and generated JSON in which the secret detectors find a literal secret is rejected.

   ```markdown
   # Sign in

   Sign in as the configured test user and verify that the dashboard heading is visible.
   ```

2. ## Review and approve the names \{#review-names}

   ```bash
   npx ambercast generate tests/ambercast/<name>.test.md
   ```

   Replace `<name>` with your prompt file name, here and in the replay command below. The shell reads a literal `<name>` as redirection.

   Generation first builds a candidate plan and lists any newly proposed secret names. In an interactive terminal, review each name and accept only the names that fit this test.

3. ## Pre-approve names in a non-interactive environment \{#preapprove-names}

   Only in CI or another non-interactive environment, add the reviewed names before you run `generate` in step 2.

   ```json
   {
     "$schema": "https://kotarotsubaki.github.io/ambercast/schemas/config.schema.json",
     "secrets": { "allow": ["password"] }
   }
   ```

   An empty `secrets.allow` requires consent for every name. The value `"*"` accepts any name the AI proposes without per-name review. It removes the approval boundary, so use it only when you accept that. When it is already `"*"`, accepting consent writes no allowlist update.

   To record accepted names, ambercast takes an exclusive update and re-reads and validates the current file. Existing names are deduplicated and keep their order. New names that are not already present are deduplicated, sorted, and appended.

4. ## Set the values in the environment \{#set-values}

   Set each value only in the command environment. `{{secrets.a.b}}` resolves from `AMBERCAST_SECRET_A_B`: dots become underscores and each segment is uppercased.

   If the secret is filled away from `baseUrl`, allow the extra origin as described in [Configure targets](/ambercast/how-to/configure-targets/).

</Steps>

## Verification \{#verification}

- After consent or an allowlist entry, generation writes the plan and records a newly accepted name in `secrets.allow`.
- The allowlist commit and the plan and grounding writes are separate operations. Every name accepted in one generation is committed once, before any candidate file is written. If generation is interrupted or fails after that commit, `secrets.allow` can be ahead of the artifacts. Rerun `generate` to recover with the names already allowed.
- If you decline consent, or consent cannot be requested in a non-interactive terminal, generation fails with `SECRET_CONSENT_REQUIRED` and writes no candidate artifacts. Add the reviewed names to `secrets.allow` and rerun.

With the required `AMBERCAST_SECRET_<NAME>` variables still in the environment, replay against a safe target.

```bash
npx ambercast run --resolve tests/ambercast/<name>.test.md
```

A `fill-secret` resolves its variable only after the live origin passes the sink-policy check.
