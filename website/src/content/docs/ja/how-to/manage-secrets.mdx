---

プロンプトにシークレットを書かず、提案された名前を承認して、値は環境変数から渡す。

## 前提条件 \{#prerequisites}

`ambercast.config.json` は、あらかじめ無くてよい。承認した同意で許可リストを残す必要があり、設定ファイルが無いときは、ambercast がそのファイルを作る。

## 手順 \{#steps}

<Steps>

1. ## シークレットを書かずにプロンプトを書く \{#write-prompt}

   プロンプトには、ユーザー成果だけを書く。グラント行もシークレットの値も書かない。生成した計画（plan）に入るのは `{{secrets.*}}` の参照だけで、リテラルのシークレットを含む JSON は拒否される。

   ```markdown
   # Sign in

   Sign in as the configured test user and verify that the dashboard heading is visible.
   ```

2. ## 名前を確かめて承認する \{#review-names}

   ```bash
   npx ambercast generate tests/ambercast/<name>.test.md
   ```

   generate は、まず候補の計画を作り、新しく提案されたシークレット名を一覧にする。対話式の端末では名前を 1 つずつ確かめ、このテストに合うものだけを承認する。

3. ## 非対話の環境では名前を先に許可する \{#preapprove-names}

   CI など対話式でない環境では、生成の前に、確かめた名前を許可リストへ入れる。

   ```json
   {
     "$schema": "https://kotarotsubaki.github.io/ambercast/schemas/config.schema.json",
     "secrets": { "allow": ["password"] }
   }
   ```

   `secrets.allow` が空なら、すべての名前に同意が要る。`"*"` は、AI が提案したどの名前も 1 つずつ確かめずに受け入れる。承認の境界がなくなるため、そのことを理解した上でだけ使う。すでに `"*"` なら、同意を承認しても許可リストは更新されない。

   承認した名前を記録するとき、ambercast は排他的に更新する。現在の設定ファイルを読み直して検証してから、既存の順序を保ったまま、新しい名前を重複なく並べ替えて末尾に足す。

4. ## 値を環境変数に置く \{#set-values}

   値は、コマンドを実行する環境にだけ置く。`{{secrets.a.b}}` は `AMBERCAST_SECRET_A_B` から解決され、ドットはアンダースコアに、各セグメントは大文字になる。

   入力先が `baseUrl` と別のオリジンなら、[ターゲットの設定](/ambercast/ja/how-to/configure-targets/)で追加のオリジンを許可する。

</Steps>

## 確認 \{#verification}

- 同意か許可リストの項目があれば、生成は計画を書き込み、新しく承認した名前を `secrets.allow` に記録する。
- 許可リストへの記録と、計画およびグラウンディングの書き込みは、別の操作である。1 回の生成で承認した名前は、どの候補のファイルよりも先に、まとめて 1 度だけ記録される。記録の後に中断や失敗が起きると、`secrets.allow` が成果物より先に進むことがある。`generate` を再実行すれば、許可済みの名前のまま回復して先へ進む。
- 同意を断った場合や、非対話の端末で同意を求められない場合、生成は `SECRET_CONSENT_REQUIRED` で失敗し、候補の成果物を書き込まない。確かめた名前を `secrets.allow` に足してから、再実行する。

必要な `AMBERCAST_SECRET_<NAME>` を環境に残したまま、安全なターゲットで再生する。

```bash
npx ambercast run --resolve tests/ambercast/<name>.test.md
```

`fill-secret` は、実際のオリジンがシンクポリシーの検査を通った後にだけ、その変数を解決する。
