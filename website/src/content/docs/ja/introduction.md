私は個人でサービスを作っている。リリースの前には、全機能を手で触って確かめる打鍵テストをやる。これが嫌いだった。画面数が増えるほど時間がかかり、しかも毎回同じことをする。

Playwright MCP が出て、この作業を AI に任せられるようになった。Claude Code に「ログインして、データを登録して、集計画面で数字を確かめて」と頼めば、ブラウザを開いて本当にやってくれる。リリース前の全機能チェックを、丸ごと AI に打鍵させるようになった。

## 従来の E2E テストが壊れすぎた {#e2e-broke}

同じ頃、私の開発はほとんど AI ループになっていた。仕様を渡し、AI が実装し、テストを回し、直す。この速さに、Playwright で書いた従来の E2E テストがついていけなかった。

AI は UI を気軽に変える。ボタンの位置、ラベル、DOM の構造。そのたびにセレクタが壊れ、テストが赤くなる。直すのも AI に任せたが、E2E の修正は一回で終わらない。直して、走らせて、また別の場所が壊れる。このループが時間とトークンを削り、テストが実装の速さのボトルネックになった。

一方で、AI に打鍵させたテストは壊れなかった。AI は画面を見て「ログインボタン」を探すので、セレクタの変更を気にしない。

ここで思った。AI による打鍵テストを資産にできれば、従来の E2E テストを大きく縮小できるのではないか。

## しかし AI に毎回打鍵させるのは資産ではない {#not-an-asset}

やってみると、別の問題があった。

- 毎回プロンプトを打ち直す。前回何を頼んだか、自分でも覚えていない
- 毎回プロダクトの機能探索から始まる。AI は前回学んだことを忘れている
- 時間がかかり、トークンを消費する。全機能となると無視できない
- 同じ指示でも、実行のたびに結果が揺れる

壊れにくいが、再現性がない。安いが、積み上がらない。これは資産ではなく、毎回やり直す作業だった。

## 意図は文章のまま、実行は計画のまま {#intent-and-plan}

このツールを作ろうと調査していたとき、「AI によるテストは再現性に問題がある」という記述を見つけた。そのときに思いついたのが、SQL の実行計画だった。

SQL は「何が欲しいか」を書き、データベースが「どう取るか」の実行計画を作る。計画は再利用され、テーブルが変われば作り直される。人は計画を書かない。

テストも同じ形にできる。テストは「何を確かめたいか」を自然言語で書く。AI はそれを一度だけ読み、実行計画を作る。初回の実行で画面との対応を覚え、二度目からは、記録が命中する限り計画をそのまま再生する。AI は呼ばれない。UI が変わって計画が合わなくなったときだけ、AI が計画や記録を直し、人がそれを承認する。

意図は文章のまま琥珀に閉じ込め、実行は鋳型から何度でも取り出す。それが ambercast という名前の由来だ。

## 誰のために {#who-for}

私はエンジニアなので、まず自分のために作った。同時に、vibe coder と呼ばれる人たちにテストの価値を知ってほしいとも思っている。AI にコードを書かせる人ほど、AI が壊したものに気づく手段が要る。テストが自然言語なら、読めるし、書けるし、AI に直させられる。
