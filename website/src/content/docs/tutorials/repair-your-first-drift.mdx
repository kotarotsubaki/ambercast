---
title: Healing a test after a UI change
description: Change the UI of a disposable practice app, then repair the failing test with an idempotent target.
---

import { Steps, LinkCard } from '@astrojs/starlight/components';

You will change a practice app's UI in a way that affects locators, reproduce the failure, and repair it.

## Prerequisites \{#prerequisites}

- You have a disposable practice application that you may change freely.
- A generated test for that application passes today. The sample from [Your first test in 5 minutes](/ambercast/tutorials/quick-start/) works.
- The target must set `healReplayIsolation` to `idempotent` before heal can run. The built-in `web-user` target and an unset key default to `stateful`, which cannot heal.

## Steps \{#steps}

<Steps>

1. ## Make the target idempotent \{#set-idempotent}

   Open the `ambercast.config.json` that `init` created. Add `"healReplayIsolation": "idempotent"` to the selected target, and keep the file's existing `$schema`.

   Change only that key. Keep the target name, `baseUrl`, `executor` (including `executor.browser`), and any `secretSinkOrigins`, and do not add, remove, or rename a target. A `targets` record replaces the default targets ([Configuration](/ambercast/reference/configuration/#file-selection)).

   A project with no configuration file writes this single line as the whole file. Every configuration file needs `$schema`, and its URL is the [published configuration schema](/ambercast/reference/json-schemas/#publication-metadata).

   ```json
   {"$schema":"https://kotarotsubaki.github.io/ambercast/schemas/config.schema.json","targets":{"web-user":{"baseUrl":"http://localhost:3000","healReplayIsolation":"idempotent"}},"defaultTarget":"web-user"}
   ```

   Target names and definitions feed `inputsDigest`, but `healReplayIsolation` resolves live and stays outside it. Your existing plan therefore stays fresh ([Configuration](/ambercast/reference/configuration/#targets)).

2. ## Reproduce the failure \{#reproduce-failure}

   Before the failing run, confirm the retention policy of the runs directory and who can read it. A completed `run` attempts to write `report.json` there and may keep a failure screenshot. [File layout](/ambercast/reference/file-layout/#run-artifacts) lists when the screenshot is omitted.

   Then make a locator-affecting UI change and run the test. Replace `<name>` with your prompt's file name, such as `find-page`.

   ```bash
   npx ambercast run tests/ambercast/<name>.test.md
   ```

   Observe the failure before you repair anything. By default, a grounding miss fails without calling AI, so the committed grounding stays unchanged.

   Pass `--resolve` only when you want live re-grounding. With the default local write-back, it can save a re-resolved fingerprint, and the run can pass without showing the drift ([ambercast run](/ambercast/reference/cli/run/#resolve)).

3. ## Preview the repair \{#preview-repair}

   ```bash
   npx ambercast heal --dry-run tests/ambercast/<name>.test.md
   ```

   The report records a completed repair as `preview-only`, and the plan and grounding writes stay unapplied. The report shows no candidate patch, so this step is an approval decision, not a diff review.

   `--dry-run` still writes attempt evidence, and failure screenshots can remain. It is not a no-write preview ([ambercast heal](/ambercast/reference/cli/heal/#preconditions)).

4. ## Apply the repair \{#apply-repair}

   Get explicit human approval first. A human at an interactive terminal runs this command and answers the CLI confirmation.

   ```bash
   npx ambercast heal tests/ambercast/<name>.test.md
   ```

   An agent or other non-interactive caller adds `--yes` only after that approval appears in the conversation.

   ```bash
   npx ambercast heal --yes tests/ambercast/<name>.test.md
   ```

   `--yes` only pre-authorizes the CLI confirmation. It never replaces human approval of an agent's write ([Setup prompt](/ambercast/agents/setup-prompt/#copy-paste-prompt)).

5. ## Check freshness \{#check-fresh}

   ```bash
   npx ambercast check tests/ambercast/<name>.test.md
   ```

   Exit code `0` shows the repaired case is fresh. Otherwise follow [Recover stale artifacts](/ambercast/how-to/recover-stale-artifacts/). See [ambercast check](/ambercast/reference/cli/check/) for details.

6. ## Review and commit the changes \{#review-commit}

   After the applied heal in step 4, run this command.

   ```bash
   git status --short
   ```

   For each changed tracked file in scope (the configuration, the changed UI file, the plan, and the grounding), show `git diff -- <path>`. For each untracked file, show its full contents or `git diff --no-index /dev/null <path>`. Present the change set and stop.

   Commit only when the conversation asks for it. Revert only after you confirm the target files and get explicit approval. The agent default is to present the diff, which keeps an agent from discarding existing changes by inference ([Review generated diffs](/ambercast/how-to/review-generated-diffs/)).

</Steps>

The no-argument `npx ambercast heal` discovers every test that matches the configured test directory, match rules, and ignore rules. This tutorial heals one named `.test.md`. Use the no-argument form only in a separately approved all-tests repair ([ambercast heal](/ambercast/reference/cli/heal/#flags)).

## Verification \{#verification}

- The selected target is `idempotent`.
- The failing case is repaired, and `npx ambercast check` exits `0`.
- You presented the change set and are waiting for a commit request.
