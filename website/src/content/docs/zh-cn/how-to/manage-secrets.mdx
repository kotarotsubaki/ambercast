---

import { Steps, LinkCard } from '@astrojs/starlight/components';

不要在 Prompt 里写机密，批准提出的名称，并通过环境变量传入值。

## 前置条件 \{#prerequisites}

不需要已有的 `ambercast.config.json`。已批准的同意需要保存许可列表而文件不存在时，ambercast 会创建该文件。

## 操作步骤 \{#steps}

<Steps>

1. ## 不带机密地编写 Prompt \{#write-prompt}

   只写用户结果，不写授权行，也不写机密值。生成的执行计划只包含 `{{secrets.*}}` 引用，机密检测器在其中发现字面机密的生成 JSON 会被拒绝。

   ```markdown
   # Sign in

   Sign in as the configured test user and verify that the dashboard heading is visible.
   ```

2. ## 审查并批准名称 \{#review-names}

   ```bash
   npx ambercast generate tests/ambercast/<name>.test.md
   ```

   生成先构建候选执行计划，并列出新提出的机密名称。在交互式终端中，逐个审查名称，只批准适用于该测试的名称。

3. ## 在非交互环境中预先批准名称 \{#preapprove-names}

   仅在 CI 或其他非交互环境中，才在步骤 2 运行 `generate` 之前，先加入已审查的名称。

   ```json
   {
     "$schema": "https://kotarotsubaki.github.io/ambercast/schemas/config.schema.json",
     "secrets": { "allow": ["password"] }
   }
   ```

   `secrets.allow` 为空时，每个名称都需要同意。值 `"*"` 会不经逐个审查，接受 AI 提出的任何名称。它会取消批准边界，只有在接受这一点时才使用。若它已经是 `"*"`，批准同意不会写入许可列表更新。

   记录已批准的名称时，ambercast 执行排他更新，并重新读取、验证当前文件。现有名称会去重并保持原有顺序；尚未存在的新名称会去重、排序后追加到末尾。

4. ## 在环境中设置值 \{#set-values}

   只在命令环境中设置值。`{{secrets.a.b}}` 从 `AMBERCAST_SECRET_A_B` 解析：点号变为下划线，各段转为大写。

   若填充发生在 `baseUrl` 之外，请按[配置目标环境](/ambercast/zh-cn/how-to/configure-targets/)允许额外的源。

</Steps>

## 验证 \{#verification}

- 同意或许可列表条目生效后，生成会写入执行计划，并把新批准的名称记录到 `secrets.allow`。
- 许可列表的提交与执行计划、定位缓存的写入是相互独立的操作。一次生成中批准的全部名称，会在写入任何候选文件之前一次性提交。如果提交之后生成被中断或失败，`secrets.allow` 可能领先于产物。重新运行 `generate`，即可用已允许的名称恢复。
- 若拒绝同意，或在非交互式终端中无法请求同意，生成会以 `SECRET_CONSENT_REQUIRED` 失败，且不写入任何候选产物。把已审查的名称加入 `secrets.allow`，然后重新运行。

在命令环境中保留所需的 `AMBERCAST_SECRET_<NAME>` 变量，对安全的目标进行回放。

```bash
npx ambercast run --resolve tests/ambercast/<name>.test.md
```

只有实时源通过 sink-policy 检查后，`fill-secret` 才会解析其变量。
