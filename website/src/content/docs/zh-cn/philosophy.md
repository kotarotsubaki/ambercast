正如上一页所说，ambercast 的出发点只有一个：把 AI 驱动的点击测试变成资产。本页按顺序说明，由这一点推导出的各项设计决策。

## 测试必须是资产 {#tests-as-assets}

所谓资产，是指写完之后价值不会随时间衰减的东西。测试要成为资产，需要满足三个条件：不容易坏、可以被读懂、不被绑定在特定工具上。

传统 E2E 测试三个条件都不满足：选择器一变就坏，代码只有作者本人能读懂，换一个框架就要重写。ambercast 的每一项决策，都是为了满足这三个条件。

## prompt 为本，实现细节为末 {#intent-primary}

测试中能长期保有价值的是意图，也就是"想确认什么"，而不是"点击哪个元素"这类实现细节。因此在 ambercast 中，用自然语言写成的 prompt 是唯一的事实来源，AI 生成的执行计划只是它的衍生物。

这种关系类似于 package.json 与锁文件：prompt 声明意图，plan 固定可重现性。人只编辑前者，后者由系统生成。

prompt 几乎不做任何加工，既不整理空白，也不规范措辞，为的是让对意图的任何修改都能在差异对比中清晰可见。

## plan 生来可以废弃重建 {#plans-are-disposable}

既然 plan 是衍生物，过时的 plan 就可以直接丢弃。ambercast 不把 plan 当作需要长期维护的产物：UI 一旦变化，就重新生成。plan 格式可以引入破坏性变更，需要重新生成的版本发布也被允许。

把需要守护的东西和可以舍弃的东西分开，才能把真正需要守护的东西，也就是 prompt 的稳定性，维护到最大程度。

## 表面简单，内里严谨 {#simple-surface-rigorous-core}

资产必须可读。所以日常接触到的只有三样东西：自然语言 prompt、截图、执行结果。目标是让非工程师读完也能明白测试在确认什么。

与此同时，可重现性、每次执行的波动、AI 调用成本这类难题，交给下层的结构化层去处理。中间生成的 plan 是人类可读的 JSON，但不需要读它也能使用。它只保证一种"想读就能读懂"的透明度，而不要求你必须去读。

## 最需要警惕的是错误通过 {#wrong-pass}

把测试交给 AI 时，最危险的情况是"明明坏了却通过"的测试。人们普遍观察到，AI 擅长让测试通过，却不擅长保持测试本身的意义。让 AI 去修复失败的测试时，它可能会削弱断言的力度，只为了让测试通过。

因此 ambercast 把断言质量放在最优先的位置，CI 中默认不进行自动修复。测试坏了就应当失败，是否修复由人来决定。修复必须显式执行，且改写要经过批准才会被应用。

## 人与 AI 都是读者 {#humans-and-agents}

资产的读者不只是人类。Claude Code、Codex 这类编码代理，也会在实现、测试、修复的循环中读写测试。ambercast 把代理当作第一等用户对待，除 CLI 之外还提供官方 skill，并计划推出 MCP。

不会为代理另写一份规范。同一份文档，要让人类和代理都能读懂。

## 资产留在本地 {#assets-stay-local}

既然称之为资产，它就必须属于用户。在 ambercast 中，prompt 和执行计划放在用户自己的代码仓库里，由 git 管理。截图和执行记录也留在用户本地。没有任何东西是由 ambercast 托管的。

执行 AI 时，使用的是用户自己已经拥有的 Claude 或 Codex 协议。ambercast 既不托管密钥，也不代付 AI 的使用费用。CLI 是开源的，完全在本地闭环运行。

未来计划提供云端版本，用于团队共享和分担繁重的计算。即便如此，资产的正本仍然在本地代码仓库中。云端只是建在其上的功能，而不是资产的存放之处。

## 拿不准时的判断标准 {#five-pains}

这些原则是为了解决五个问题而选择的：脆弱的 E2E 测试、难以读懂的测试代码、手动点击测试的人力消耗、把测试变成资产的困难，以及 vibe coder 面临的测试难题。每当难以判断是否要新增某项功能时，ambercast 都会回到这五个问题上重新权衡。
